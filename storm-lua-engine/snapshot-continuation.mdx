## 概要

スナップショットは、実行中のVMの状態をバイト列として保存し、後から別のVMへ復元する仕組みです。復元はソースを再実行せずに行います。プロセスの再起動をまたいだ再開、別プロセスへの状態の移行、チェックポイントからの復旧に使えます。

土台は全プロファイル共通の`Vm`のスナップショットです。MicrocontrollerとAddonには、プロファイル固有の状態も一緒に運ぶ継続（continuation）が用意されています。Component Modにはプロファイル単位の継続はありません。

この機能はRust APIです。TypeScript SDKとWASMには、v0.5.0ではスナップショットを公開していません。

## VMスナップショット

```rust
let bytes = vm.snapshot()?;   // Vec<u8>
vm.restore(&bytes)?;
```

取得と復元はどちらもアイドル境界（コールバックを実行していない時点）で行います。実行中のコールバックがあるVMや、失敗状態のVMは型付きエラーで拒否します。

保存対象は、サンドボックス環境テーブルを根とする到達可能グラフ全体です。テーブル・クロージャ・アップ値セルは同一性を保持し、循環もそのまま往復します。ホストが種付けした値はシンボリックなパス参照として記録され、復元先VMの対応する現行インスタンスへ再束縛されます。再実行は一切行いません。

復元先のVMは、スナップショット元と同じ環境プロファイルで構築し、同じホスト値を種付け・登録しておく必要があります。環境テーブル自体は同一オブジェクトのまま、内容だけがスナップショット時点の状態へ戻るため、同期コールバック等が保持する環境ハンドルと矛盾しません。

復元はトランザクションではありません。復元中にエラーになったVMは部分的に変更されている可能性があるため、エラーを受けたらそのVMは破棄してください。

## 継続：ヒープの外の状態

スナップショットが運ぶのはヒープだけです。乱数ストリームのようにヒープの外で状態を持つものは、継続APIで明示的に往復させます。復元の順序は「ヒープ→ヒープ外」で、復元後は同じ列が続きます。

`math.random`のストリーム状態は`random_stream_state()`で取得し、`set_random_stream_state(state)`で設定します。値の型は`RandomStreamState`で、エンジン所有ストリームの`Engine`、組み込みCRTストリームの`BuiltinCrt`、ホスト所有ストリームを示す`HostOwned`の3種があります。ストリームの種類と一致しない状態は`InvalidArgument`で拒否します。ホスト共有CRTストリームのVMでは状態はホストのものなので、設定は`Unsupported`で拒否します。黙って無視はしません。

Microcontrollerでは、ヒープに加えて次の状態を往復できます。

- エラーステータスとエラーリング（最大11件）は`error_continuation()` / `restore_error_continuation(...)`で運びます。復元時に値域を検証し、不正なステータスや件数超過は拒否します
- HTTPの継続カーソルは`http_continuation_cursor()` / `restore_http_continuation(cursor)`で運びます。飛行中の要求は再開できないため、先に要求を排出してからカーソルを取得します。復元したキューは新しい世代になり、旧トークンは無効化されます

## Addonの継続

Addonの継続は、ヒープ・ライフサイクル・プロパティ・エラーステータスを1つのバイト列（SLADDON v2形式）にまとめたものです。

```rust
let bytes = addon.snapshot()?;
let addon = Addon::from_snapshot(config, &bytes)?;
```

`Addon::from_snapshot`は新しいホスト束縛を構築して復元します。ソースの再読み込みも、`onCreate`の呼び出しも行いません。取得時と同じホストAPI・プロファイル・制限を`config`に渡してください。古いコールバックハンドルは再利用されません。復元に失敗した候補は破棄され、部分的に復元されたAddonが返ることはありません。

次の状態では取得を拒否します。

- 未処理の組み込みHTTP要求が残っている
- 開発用のrequireキャッシュがある
- 未配送のログ記録が残っている

また`from_snapshot`側では、savedataやrequireローダーを含む`config`を拒否します。継続と併用はできません。ホストサービス（ホストが導入したCRTストリームを含む）は引き続きホストの責任です。

Addonの保存・復元全般は[Addonの組み込み](/storm-lua-engine/addons)も参照してください。

## 形式の互換性

VMスナップショットの形式には版があり、現行は版1です。版の一致しないデータは型付きエラーで拒否します。黙って読み替えたり、初期状態で代用したりはしません。復元先の環境プロファイルが一致しないスナップショットも拒否します。

対応できない値が到達可能な位置にある場合、保存は`ErrorKind::Unsupported`で失敗します。対象はスレッド、ユーザデータ、メタテーブル付きテーブル、未登録のホスト関数です。本番プロファイルではいずれも生成できないため、出現はバグの兆候として扱います。

Addon継続の現行形式はSLADDON v2です。v1形式のデータは明示的に拒否します。旧版で取得したAddon継続データをv0.5.0で読み込むことはできません。

## Send + Sync

ホストが共有するハンドル類を`Arc`ベースへ移し、`Send + Sync`にしました。対象は共有CRT乱数（`SharedCrtRandom`）、ホストコール制御（`HostCallContext`）、ログリーダー（`LogReader`）、requireローダー（`RequireLoader`）です。

これにより、ホストはこれらのハンドルをスレッド間で共有できます。例えば、VMを駆動するスレッドとは別のスレッドからログを読んだり、デバッガの実行制御ハンドルを共有したりできます。

スナップショットの検証記録は[検証ドキュメント](https://github.com/Stormcat-Works/storm-lua-engine/blob/v0.5.0/docs/verification/vm-snapshot-20261104.md)にあります。
