<Note>
v0.3.0のJavaScript・型定義・WASMを一組で使用します。SDKはマップの生成と検証までを提供し、エディタの表示・保存・実行位置との接続はホストが担当します。
</Note>

## 生成する

`npm install @stormcat-works/storm-lua-engine@0.3.0`で導入します。`@stormcat-works/storm-lua-engine/compiler`の`loadCompiler`を初期化し、単一ソースは`compiler.minify(source, {sourceMap:true, sourceName:"controller.lua"})`へ渡します。

複数ファイルでは`compiler.build(project, {minify:true, sourceMap:true})`、LifeBoatのinclude-once方式では`compiler.buildLifeboat(project, {minify:true, sourceMap:true})`を使用します。元moduleへの位置合成はSDKが行います。map内のファイル名は表示名であり、SDKがディスクからそのファイルを開くわけではありません。

コンパイラを初期化した後の基本操作は次のとおりです。

```ts
const result = compiler.minify(source, {
  sourceMap: true,
  sourceName: "controller.lua",
});
if (!result.ok || result.code === undefined || result.map === undefined) {
  throw new Error(JSON.stringify(result.diagnostics));
}
const artifact = { code: result.code, map: result.map };
const details = compiler.validateSourceMap(artifact.code, artifact.map);
```

通常のminifyは明示指定時だけ詳細追跡を有効にします。非短縮`build({minify:false})`が標準mapを返す従来動作は維持し、`sourceMap:true`で詳細拡張も追加します。マップ有無で生成Luaの短縮結果は変わりません。

マップはゲームへ貼り付けるLuaとは別の成果物です。`code`だけを実行し、`map`はホスト側へ保管します。8192文字制限のLuaへマップを埋め込む必要はありません。

## 同じ組を検証・保存する

`map`はSource Map v3形式のJSON文字列です。標準の`sources`、`sourcesContent`、`names`、`mappings`に加え、`x_storm`へ詳細な由来・理由が入ります。

`validateSourceMap(code,map)`は、生成コード・原文snapshot・設定・mapの指紋、範囲・参照、標準mapと詳細情報の整合性を検証し、型付きの`OptimizationMap`を返します。読み込んだJSONに型アサーションを付けるだけで検証済みにしないでください。フィンガープリントは内容の整合性検査で、発行者を保証する署名ではありません。

`details.producer.version`は生成したエンジン版、`details.schemaVersion`は独自形式の版です。Source Map本体の`version:3`とは別です。独自に配信していた旧`compiler.js`や`compiler_bg.wasm`も、npmパッケージと同じ版へ更新します。古いWorkerやService Workerのキャッシュも残さないでください。

<Warning>
マップは原文全文と、固定化したproperty等の設定を含みます。共有先を確認してください。生成後のLuaに別のminify、文字の追加、改行変換、前置きコードの挿入をすると元のマップとは組み合いません。SDKで再生成するか、別変換の正しいマップ合成が必要です。
</Warning>

## 標準の位置を引く

標準readerを利用するホストでは、`npm install @jridgewell/trace-mapping`などでconsumerを追加できます。これはホストの任意の依存で、SDK自体の実行時依存ではありません。

```ts
import { TraceMap, originalPositionFor } from "@jridgewell/trace-mapping";

const position = originalPositionFor(new TraceMap(artifact.map), {
  line: generatedLine,     // 1始まり
  column: generatedColumn, // 0始まりのUTF-16列
});
```

生成位置はエディタなどから実際に取得した値を使います。`position.source`がnullなら、近い原文の行へ勝手に移動しません。標準readerの検索はマップにあるアンカーを使います。厳密なUnknown範囲・copy内部・複数の関連元・削除状況は、詳細情報も参照します。

## 理由と複数の関連元を表示する

`details.mappings`は生成Lua上の非重複な範囲表です。`start`以上`end`未満の位置がその区間に属し、`origin`は`details.origins`のindexです。`origin:null`はUnknownであり、自動生成とは異なります。

| 情報 | 読み方 |
| --- | --- |
| 主な元範囲 | origin.primaryのsource indexとstart/end |
| 精度 | name / token / expression / statement / group |
| 自動生成 | origin.kindがsynthetic。架空の元位置を持たない |
| 最適化理由 | origin.reasonsをdetails.reasonsへ解決 |
| 関連元 | origin.relatedをdetails.relationsへ解決。definition/callSite/argument等のroleを持つ |
| インライン文脈 | mapping.inlineContextsをdetails.contextsへ解決 |
| 親の式や文 | details.constructsから選択範囲を含む構文を確認 |
| 削除・置換 | details.dispositionsの元範囲・reason・既知の置換元を確認 |

理由は`code`と`operation`、記録された場合の`basis`と`facts`を持ちます。根拠がnullの場合、表示側がパス名から判断値を推測しません。

例えば、通常のtolerant設定で`2*3`が`6`になった場合、生成`6`は元の式全体と定数評価の理由へ対応します。関数のインライン化では、定義側のリテラルをそのまま示しながら、呼び出し元の文脈も取得できます。exact/tolerantやパス設定が異なると、選ばれる変換も異なります。

詳細の範囲は**UTF-8バイトの半開区間**、JavaScript文字列のindexや一般的なエディタ位置は**UTF-16**です。日本語・絵文字を含むコードで単純に同じ数字として扱わないでください。検証済みの`copied`区間は同一バイトのコピーなので内部位置を写せます。変換された式や広いgroupを文字単位で補間してはいけません。

## Nodeで実行する例

[optimized-source-map.mjs](https://github.com/Stormcat-Works/storm-lua-engine/blob/v0.3.0/examples/consumer/optimized-source-map.mjs)は、インストールしたSDKのWASMを読み、map生成・検証、標準位置、理由・関連元、インライン文脈、古いmapの拒否を確認します。

`npm install @stormcat-works/storm-lua-engine@0.3.0 @jridgewell/trace-mapping`の後、同ファイルを保存して`node optimized-source-map.mjs`で実行できます。Node 22.18以降のESMを使用します。コードからLuaを実行する例ではありません。

非短縮プロジェクトの実停止・ステップ・エラー位置を接続する例は[source-map.mjs](https://github.com/Stormcat-Works/storm-lua-engine/blob/v0.3.0/examples/consumer/source-map.mjs)です。こちらは元moduleをビルドしてVMへ明示loadし、実行結果も確認します。

## ブラウザーとWorker

ブラウザーではコンパイラをホスト所有のmodule Workerへ置き、`/compiler-worker`の`serveCompiler`と`CompilerWorkerClient`で接続できます。`await client.minify(source,{sourceMap:true})`、`await client.validateSourceMap(code,map)`が対応します。Worker生成・終了と、同じ版のJS/WASMを配信する設定はホスト側です。

コンパイルと理由JSON生成には追加の仕事量があります。`validateSourceMap`もコンパイラ側へ依頼できるため、UIスレッドで大きなマップを繰り返し検証する必要はありません。得られた検証結果を同じ成果物IDに紐付けて使用します。

[Playground](/storm-lua-engine/playground)のSource Map例では、元コードと生成コードを双方向に選択し、理由・複数の候補・除去記録を確認できます。既存エディタへ自動的にUIが追加されるわけではありません。

## 実行位置とブレークポイント

VMの`load`には生成`code`と安定したチャンク名を渡します。ホストはそのチャンク名・実行世代と対応mapを保持し、元範囲から生成行の候補を取得して`vm.setBreakpoints()`へ設定します。停止したstack、ログ、エラーの生成位置を同じmapで元位置へ戻します。

マップを作成しても、VMが返す行の精度が列や命令位置へ自動的に増えるわけではありません。**行しか分からない場合は、その生成行に対応する元位置を候補として示します。** 1行に圧縮されたLuaでcolumn=0を任意に指定し、それを実際の失敗位置として表示しないでください。

削除された原文に実行箇所がない場合、近くの生成行へbreakpointを移しません。copy区間にコメントの位置があっても、そこが実行可能な停止箇所とは限りません。元変数の値・寿命、インライン化で消えた実frame、特定のloop反復や過去の実行状態は、この静的マップだけでは復元しません。

## lintと前処理

`analyze(project)`は元moduleを直接解析します。lintのためだけに先にminifyする必要はありません。SDKのリンクやLifeBoat開発区間の除去を使う場合、対応するビルド経路が元位置を管理します。

ホストがSDKへ渡す前に独自の文字削除・連結などを行う場合、その前処理とエディタ原文の対応は別途必要です。前処理後の位置を元の編集バッファの位置とみなさないでください。
